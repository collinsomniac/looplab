documentation, or our own device measurements), **[R]** reported by the source but not reproduced by

## 1. ninfer — the most useful single resource

**What it is [V]**: Apache-2.0, ~2.9k stars, created June 2026, actively maintained. C++/CUDA for
*one* GPU (RTX 5090, `sm_120a`) and *selected* checkpoints (Qwen3.6/3.8 27B dense, 35B-A3B MoE).
Single resident model, 1–8 execution lanes fixed at startup. Their thesis is ours: specialise to
one model on one device and win by not being general.

### 1a. Prefix caching for hybrid (recurrent) models is a checkpoint problem, not a KV problem
From `docs/maintainer/resource-scheduling-and-context-cache.md` (Chinese; translated here) [V]:
- Hybrid models (Qwen3.5 has **GDN/linear-attention layers**: 48 of 64 layers in the 27B) cannot
  rewind recurrent state. Reusing a prefix needs **a complete state image at that exact token**
  *plus* contiguous KV. "KV can be shared page by page; recurrent state is a whole-position
  snapshot."
- So they manage three units: **continuation records** (where a history can resume), **checkpoints**
  (exact position + state image + KV coverage), and **physical objects** (actual memory).
- They checkpoint at **semantic boundaries, not chunk boundaries**: the generation endpoint `E`,
  and a typed input point `R` *just before the assistant header* — which survives the two common
  agent rewrites: retrying a response, and a client normalising a tool call in the history.
- **"Prefill chunk boundaries do not save state."** Saving is driven by input semantics and request
  lifecycle.
- Retention is driven by **evidence of real reuse** (actual adoption, or two different requests
  recomputing the same prefix), with a soft target of ¾ of each pool and eviction by *marginal
  recompute tokens lost per byte freed*.

**Why this matters for us — this exposes a bug in the fork code I wrote today [I, but certain]**:
`LocalModelHost.stream` reuses a cached `ChatSession` only if the previous transcript is an exact
prefix of the new one. The OpenMinis agent loop *rewrites history* (tool-call normalisation,
compaction, offload stubs that replace payloads — see their `isOffloadedArgument` /
`isOffloadReadback` flags). Any rewrite anywhere breaks prefix equality and forces a full re-prefill,
which on the phone is the dominant latency. ninfer's typed `R` point is exactly the fix: keep a
checkpoint **before the last assistant turn** as well as at the end, so a rewrite of the last turn
falls back one turn instead of to zero. Strata's `MESSAGE_BOUNDARY_CACHE` independently arrives at
the same answer (§3).

**And it explains a measured anomaly [I]**: Qwen3.5 is a hybrid model (llama.cpp #26004 lists
"Qwen3.5 / Qwen3-Next" among hybrid/recurrent models that "cannot rewind their state without a
checkpoint" [V]). In MLX, hybrid models get a different cache type than pure attention, so prompt
caching and speculation behave differently for Qwen3.5 than for Qwen3. That is a plausible
contributor to Qwen3.5's slower decode per byte in battery 09 (Qwen3.5-4B 25 tok/s at 2.6 GB
vs Qwen3-4B 27 tok/s at 2.3 GB). Testable: compare `cacheStatus().isHybrid` and per-token time.

### 1b. Speculative decoding on recurrent models needs replayable state
`docs/maintainer/replayssm-gdn.md` [V]: a GDN recurrent state is an FP32 matrix per head —
**144 MiB per full state for the 27B**. Speculative verify computes T draft positions, but only the
accepted prefix m is committed. Saving every intermediate state costs T×144 MiB of writes.
Their **ReplaySSM** keeps only the committed state plus compact raw inputs `(k, v, g, β)` per
position, then **replays the accepted prefix**. The subtle point they stress: the replay must use
the *exact same finite-precision computation order* as verify, or state drift accumulates across
rounds. "Algebraically equivalent" is not enough.
**For us**: speculation on Qwen3.5 targets is harder than on Qwen3 for this reason [I]; and the
drift warning is a direct analogue of our "speculative output not identical" finding (§5 of FINDINGS-R5).

### 1c. Measurement discipline we should copy
`docs/performance/methodology.md` [V]:
- **Decode rate = (completion tokens − 1) / decode seconds** — the first token belongs to prefill.
  Ours includes it, which inflates short-output rates.
- **Server TTFT = prepare + vision + prefill**, separated from ingress queueing.
- **Fixed fixture identity**: prompts, seeds and send order pinned so runs are comparable over months.
- **Steady-state windows only**: exclude ramp, prefill, recovery, drain.
- **Prefix reuse disabled** in published throughput runs, reported separately.
- Spec metrics: **acceptance = accepted/drafted**, **tokens per round = 1 + accepted/rounds**.
These are concrete upgrades to our batteries (§7).

### 1d. Headline numbers (RTX 5090) [R]
Qwen3.6-35B-A3B groupwise-int: **642 tok/s** single-request decode with MTP3 (68.6% acceptance);
**17,705 tok/s** prefill at 7.7k tokens. Dense 27B: 186–202 tok/s. These are 1.8 TB/s-class numbers
— the bandwidth ratio to our 76.8 GB/s is ~23×, which roughly matches the speed ratio to what we
see, so it is a sanity check of our bandwidth model rather than a target.

## 2. llama.cpp — two PRs that change our speculation plan

**#29869 (merged 2026-10-05) "metal: few-row MMA mat-mul … for speculative decoding"** [V]:
> "Speculative decoding verifies a few draft tokens per step… so the model runs mat-muls with 2..16
> rows. On Apple GPUs without the tensor API (M1 to M4), Metal runs these with the mat-vec kernels,
> **whose time grows with each row**."

Their M3 Ultra numbers [R]: batched decode at B=4 went 36.3 → 76.1 tok/s; DFlash2 speculative code
decoding went **30.2 → 110.0 tok/s** (serial baseline 32), prose 16.8 → 62.6. Before the fix,
speculation was *slower* than serial — the same pattern we measured (0.6B→1.7B ≈1.05×, prose 0.6–0.9×).

**Does MLX on our phone have the same problem? Checked the code [V]**: MLX's `dispatch_qmv`
routes 2+ rows to `qmv_wide`, "which reuses each weight group across the M vectors", for affine
quantisation on GPU generation ≥15; and `get_qmv_batch_limit` keeps up to 13–33 rows on the
vector path for gen ≥17 before switching to `qmm`. So MLX already does the weight-reuse trick
llama.cpp just added. The open question is whether A19 Pro reports gen ≥15 — our Metal bench
showed batched reads costing ~nothing (B=8 ≈ B=1, 66.8 GB/s), which suggests yes [I].
**Consequence**: our speculation ceiling is *not* the kernel, it is draft cost and acceptance.
The levers are therefore the ones llama.cpp/ninfer use: a **drafter that is nearly free** —
MTP heads (Qwen3.5-9B-MTP exists in mlx-community) or DFlash-style block drafters — rather than a
separate 0.6B model costing ~25% of a 4B per token.

**#29887 (merged 2026-10-07) "GPU cache for MoE experts kept in host memory"** [V]: LRU expert
cache, only misses uploaded, small batches only; "10% of the total expert size is good". On
Qwen3.8-Flash-Next (65 GB of experts) an RTX 5090 went 30.8 → **67.8 tok/s at 89% hit rate** [R].
**For us**: this is the measured answer to our open MoE question. Hit rates of 72–89% with a cache
of 10–30% of experts mean expert reuse across tokens is high. On the phone, flash is the "host" tier
(1.4–3.6 GB/s measured) and RAM is the cache. A 35B-A3B at 4-bit (~20 GB) with a ~4 GB expert
cache is plausible *if* the hit rate transfers [I] — and we can measure the hit rate on OLMoE,
which fits entirely, by logging router choices.

**#26004 (merged 2026-10-08) context checkpoints across save/restore** [V]: confirms §1a —
hybrid/recurrent models need checkpoints to travel with saved sessions, or the next divergent
prompt forces full re-processing.

**#30209** [V]: Metal flash-attention kernels added for K/V head-dim pairs (128/96 etc.). Minor for us.

## 3. The video — Strata, and a supply-chain warning

"maybe wait on this one", Unbiased Bob, 16 min, ~15k views [V]. I could not retrieve the
transcript (caption fetch blocked in the browser), so this section rests on the description's
chapters and links, which I followed to their primary sources.

**Strata** ([Niko1221/Strata](https://github.com/Niko1221/Strata), MIT, ~20k stars, pushed today) [V]:
runs Qwen3.8-Flash-Next (125B MoE, 24,576 experts, 10 per token) on a 12 GB gaming GPU.
- **Hot experts on the GPU, all experts in RAM, a lookup table on SSD**; CPU computes the misses
  in parallel. On an RTX 5070 (12 GB): 53–94 tok/s depending on quantisation [R].
- **Guess-and-check speculation**: "the same answer, 1.6–1.8× sooner" [R].
- **Prefill in large chunks** (up to 8,192 tokens) at >1,000 tok/s.
- Their opt-in docs are small, honest, measured changes worth reading as a genre:
  `MESSAGE_BOUNDARY_CACHE` (save a checkpoint at the previous turn boundary, so editing the last
  user message reuses the long history — **first-edit time −33%** [R]), `PROMPT_CACHE_TAIL`
  (one extra checkpoint near the prompt end), `KV_PREFETCH` (overlap uploads with compute:
  −5% prefill at 32k, nothing at 8k [R]), `DISJOINT_EXPERT_CACHE` (don't hold the same expert on
  two GPUs: +15% [R]). Each one states the validation environment, the ABBA comparison design, and
  explicitly what is *not* claimed. That is the reporting standard we should hold ourselves to.

**The critique (from the description) [V]**: "Don't paste stuff into your agent as a general
strategy for installing untrusted software. Don't allow your inference framework to auto-update and
require network for the build process. The deployment model should support clone; rsync to an
offline device; run make." Strata's README literally offers "Let your AI set it up — paste this
into it". His fork, **UnbiasedStrata**, removes the Python and pins llama.cpp as a submodule: "one
C++ binary, no downloads at build or start" [V].

**This applies to us directly [I]**:
- Our CI fetches dependencies by **branch name** (`mlx-swift-lm` at `branch: ouro-3.32.3`;
  OpenMinis' `deps/ish` submodule tracks `master`; Homebrew installs floating versions). A force-push
  upstream would silently change what we build. **Action: pin by commit**, and record resolved
  versions in each release's notes.
- Models download from Hugging Face by repo name at runtime. **Action: record and check file
  hashes** in the library marker (`.looplab.json`), so a changed upstream repo cannot swap weights.
- The deploy pipeline holds an Apple ID session; anything that runs in CI should never see it
  (it doesn't today — signing happens only on the desktop).

## 4. SwiftUI for iOS 27 — one item matters right now

[V] from the article (WWDC26 sessions 269/271 cited):
- **`ContentBuilder` unifies SwiftUI's result builders** specifically to fix "The compiler is unable
  to type-check this expression in reasonable time". Apple: "a substantial improvement in type
  checking performance … when building using Xcode 27". Holly Borla (WWDC26): "This year we focused
  a lot on mitigating that error in nested closures and SwiftUI view bodies."
- **The fork's build is failing on exactly this error today** — `Views/ContentView.swift:2153`, a
  view body with ~28 chained top-level modifiers in an 8,783-line file, on Xcode 27.0 (27A266a).
  So the improvement is real but not complete. Short-term fix (applied): raise the solver threshold
  in CI. Long-term: split that body into sub-views — which is also what the type-checker work rewards.
- **iOS 27 makes the UIKit scene life cycle mandatory** ("an app built with the latest SDK that has
  not adopted it fails to launch"). Checked: OpenMinis already uses a `UIWindowSceneDelegate`
  via `configurationForConnecting` [V]. LoopLab is pure SwiftUI `WindowGroup`, which is scene-based.
- Useful for the fork's UI later: `reorderContainer` + `reorderable()` (model library ordering),
  `alert(error:)` with `LocalizedError` (our intent errors already conform), toolbar
  `visibilityPriority` + `ToolbarOverflowMenu` (the chat toolbar is crowded), `NavigationTransition.crossFade`.
- Caveat the author makes himself: June beta seeds; `toolbarMinimizeBehavior` already vanished.

## 5. UL benchmarks — sustained performance is ~76% of peak

Crowd medians for iPhone 17 Pro Max [V]: Wild Life Extreme 5,405; Solar Bay 10,944;
**Steel Nomad Light stability 76–77%** (best-to-worst loop ratio). The page itself notes medians
include hot devices and background apps.

**For us [I]**: an independent population-level figure that sustained GPU work on this phone settles
around three-quarters of peak. Our own run today showed the same shape inside one battery: the
re-baseline ran twice; second pass thermal went nominal → fair → **serious**, and Qwen3-4B fell
27.4 → 21.8 tok/s (**80%**), Qwen3-0.6B 164 → 149. Separately, the earlier 36–38 GB/s state that
cleared on reboot was *not* thermal (reported nominal). So we now have two distinct phenomena:
thermal throttling (~20–25%, matches UL) and a power-state degradation (~45%, cleared by reboot).
Batteries should therefore (a) record thermal per step — done — and (b) start with a Metal bench as
a health gate and refuse to report absolute numbers below ~60 GB/s.

## 6. uiverse Galaxy

MIT, 3,815 files: 1,231 buttons, 726 cards, 718 loaders, 260 toggles; last updated 2024-09 [V].
Each is a small HTML/CSS snippet (median loader ~1.3 KB). It is not a Swift library and nothing can
be imported. **Use [I]**: a visual reference for the states our UI currently renders poorly —
model *loading* (a 2–4 s read), *prefilling* (the silent gap before the first token), *thinking*,
and *throttled*. OpenMinis already has `ShimmerOverlay` and `TypingIndicator` in
`AssistantBlockView.swift`; the gap is that the local engine has phases cloud providers don't, and
they deserve distinct, honest indicators (e.g. "reading 2.3 GB from storage", "prefill 1,240 tokens").
Attribution to creators is requested though not required.
